Provider Layer Changes — Necessity Analysis

Branch thu/openssl-aes — why every change in AESGCMCipher.java, GCMCipher.java, and CCMCipher.java is necessary and cannot be moved to the adapter or native layer. Updated after reviewer feedback on AESGCMCipher changes.

Legend: OpenSSL-specific needed only because of the OpenSSL backend   JCE correctness fixes a spec violation in both backends   Both backends pre-existing bug that affects OCK too   Cleanup dead code / cosmetic

1 · AESGCMCipher.java

1a — finalCalled flag + updateAAD-after-doFinal guard

JCE correctness

A new boolean field finalCalled is set in resetVars(false) (called after every successful doFinal) and cleared in internalInit. Both engineUpdateAAD overloads throw IllegalStateException if finalCalled && encrypting.

Why necessary: The existing requireReinit flag is set only when the same key+IV pair is reused (NIST SP 800-38D restriction). After a successful encrypt doFinal with a fresh IV, requireReinit remains false and checkReinit() passes silently. Without finalCalled, a caller can call updateAAD on the same cipher object immediately after doFinal without re-initialising — violating the JCE CipherSpi state machine. Confirmed needed to match Oracle behaviour.

Why it cannot move to the adapter: This is CipherSpi state tracking in the Java cipher layer. The adapter never sees the call sequence — it only receives individual native dispatch requests. State management must live in AESGCMCipher.

Note on the auto-IV reuse flow: After a successful doFinal encrypt, generateInternalIV pre-generates the next IV. If the caller does not call init before the next encrypt, the pre-generated IV is automatically applied at the top of the next doFinal. finalCalled is cleared in internalInit only, so calling updateAAD without re-init is still blocked for this path — which is correct: updateAAD may not be called between two doFinals; the caller should call doFinal directly with the new plaintext.

✔ Keep in AESGCMCipher.java. Confirmed by reviewer — matches Oracle behaviour.

1b — engineUpdateAAD concatenation (byte[] and ByteBuffer overloads)

Reverted — left as original

Original behaviour (restored): each engineUpdateAAD call replaces authData entirely.

+ this.authData = new byte[len];
+ System.arraycopy(src, offset, authData, 0, len);

Reviewer decision: The replacement behaviour has been present since the initial load of the repository and existed for a deliberate reason that has not been fully determined. Rather than risk introducing a regression, this change is not made until the original intent is confirmed by researching the IBMJCEPlus git history. Additionally, the intended usage model is: after doFinal, the instance is reused via a new auto-generated IV; the caller provides fresh AAD for each encrypt operation and would not expect accumulation from a prior session.

If tests fail due to AAD behaviour: the fix should be made in the backend so that the native layer correctly handles the single-call AAD replacement, rather than by changing the Java accumulation logic.

✘ Not changed. Reverted to original. Requires further investigation before modifying.

2 · GCMCipher.java

2a — Remove useJavaTLS static field and dead else { return 0; } branch

Cleanup

useJavaTLS was always true. The entire getGCMContext body was wrapped in if (useJavaTLS) { ... } else { return 0; } — the else branch was unreachable dead code. Removing the wrapper de-nests the logic with no functional change.

✔ Keep. Pure dead-code removal. No functional impact on either backend.

2b — getGCMContext: static → instance method; remove explicit provider/nativeInterface parameters

OpenSSL-specific

Before: private static long getGCMContext(boolean encrypting, int keyLength, OpenJCEPlusProvider provider, NativeInterface nativeInterface)
After: private long getGCMContext(boolean encrypting, int keyLength) — uses this.provider and this.nativeInterface.

Why necessary: GCMContextPointer now calls nativeInterface.create_GCM_context(keySize) instead of the no-arg overload. Since nativeInterface is an instance field, the method must be an instance method to call it through the correct backend. A static method cannot dispatch polymorphically through NativeInterface.

Why it cannot move to the adapter: getGCMContext manages twelve ThreadLocal<GCMContextPointer> caches (encrypt/decrypt × 3 key sizes × FIPS/non-FIPS). This is Java-layer context lifecycle management that lives in GCMCipher.

✔ Keep in GCMCipher.java. Required structural change to support OpenSSL backend dispatch.

2c — default: case added to switch in getGCMContext

Both backends

Before: an unrecognised key length left gcmCtxBuffer = null causing a NullPointerException with no diagnostic information.
After: throw new NativeException("Unsupported AES key length for GCM: " + keyLength + " bytes").

Why it cannot move to the adapter: This guard is in GCMCipher's switch before any adapter call is made. The adapter never sees an invalid key length — it is blocked here first.

✔ Keep in GCMCipher.java. Defensive improvement for both backends.

2d — FastJNI condition guards in doGCMFinal_Decrypt and doGCMFinal_Encrypt

OpenSSL-specific

A leading GCMHardwareFunctionPtr != -1 clause is added to the outer if that gates the FastJNI / hardware sub-branch.

- if (iv.length + key.length + aadLen <= FastJNIParameterBufferSize && ...
+ if (GCMHardwareFunctionPtr != -1
+         && iv.length + key.length + aadLen <= FastJNIParameterBufferSize && ...

Why necessary: When the pointer is -1 (OpenSSL backend — do_GCM_checkHardwareGCMSupport returns -1) the entire FastJNI block must be skipped. The inner else sub-branch calls do_GCM_decryptFastJNI / do_GCM_encryptFastJNI which throw UnsupportedOperationException on the OpenSSL adapter. Without the guard, this caused 33 test failures when the branch was reached.

Why it cannot move to the adapter: The condition is evaluated in GCMCipher before any adapter call is made. The adapter has no way to prevent the call — it can only throw after being called. The guard must live where the branching decision is made.

✔ Keep in GCMCipher.java. Required to prevent OpenSSL adapter from receiving unsupported calls.

2e — GCMContextPointer constructor: add keySize parameter; call create_GCM_context(keySize)

OpenSSL-specific

Before: GCMContextPointer(NativeInterface nativeInterface, OpenJCEPlusProvider provider) → nativeInterface.create_GCM_context()
After: GCMContextPointer(NativeInterface nativeInterface, OpenJCEPlusProvider provider, int keySize) → nativeInterface.create_GCM_context(keySize)

Why necessary: The OpenSSL backend must call EVP_CipherInit_ex with the correct EVP_CIPHER object (EVP_aes_128_gcm / _192_ / _256_) at context-creation time. This choice is encoded in the algorithm name passed to NativeOpenSSLImplementation.CIPHER_create. Without knowing the key size at construction, the context defaults to AES-128 and subsequent operations with a 256-bit key produce wrong results.

OCK impact: NativeOCKAdapter.create_GCM_context(int keySize) ignores keySize and delegates to the no-arg overload — zero functional change for OCK.

Why it cannot move to the adapter: GCMContextPointer is the correct owner of context lifetime and creation. The keySize is available here from key.length passed into getGCMContext.

✔ Keep in GCMCipher.java. OpenSSL requires key size at EVP context creation.

2f — do_GCM_FinalForUpdateEncrypt: output-buffer check + rc-before-arraycopy reorder

Both backends

Sub-fix 1 — rc before arraycopy:

- System.arraycopy(tag, 0, output, outputOffset + inputLen, tagLen); // tag written BEFORE rc check
- outLen = inputLen + tagLen;
- if (rc != 0) { throw new NativeException(...); }
+ if (rc != 0) { throw new NativeException(...); }  // rc checked FIRST
+ System.arraycopy(tag, 0, output, outputOffset + inputLen, tagLen);
+ outLen = inputLen + tagLen;

On main, if the native call fails the tag is written into the caller's output buffer before the exception is thrown — leaking uninitialised or partial ciphertext. Moving the rc check first prevents this.

Sub-fix 2 — output-buffer-size check:

+ if (output.length - outputOffset < inputLen + tagLen) {
+     throw new ShortBufferException(...);
+ }

The earlier getOutputSize check uses the Update-path calculation. This second check asserts the exact number of bytes (inputLen + tagLen) that will be written by System.arraycopy, catching an off-by-one buffer before any native call or data copy is made.

Why these cannot move to the adapter: The System.arraycopy of the tag and the rc check are both in GCMCipher. The adapter's do_GCM_FinalForUpdateEncrypt returns an int rc — the caller (GCMCipher) is responsible for acting on it. Moving the rc check into the adapter would require the adapter to also perform the arraycopy, conflating two responsibilities.

✔ Keep in GCMCipher.java. Pre-existing bugs that affect OCK too — candidates for upstreaming to main independently of the OpenSSL work.

3 · CCMCipher.java

3a — FastJNI condition guards in doCCMFinal_Decrypt and doCCMFinal_Encrypt

OpenSSL-specific

Same pattern as GCMCipher Change 2d. On main, CCMHardwareFunctionPtr is initialised to -1 at class level and never updated for z/OS-disabled hardware. Without the leading CCMHardwareFunctionPtr != -1 outer guard, the inner else branch calls do_CCM_decryptFastJNI / do_CCM_encryptFastJNI which throw UnsupportedOperationException on the OpenSSL adapter.

Why it cannot move to the adapter: Same reasoning as GCM — the branching decision is made in CCMCipher before any adapter call. The guard must live at the decision point.

✔ Keep in CCMCipher.java. Required to prevent OpenSSL adapter from receiving unsupported calls.

3b — tempInput sizing fix in doCCMFinal_Encrypt

Both backends

Before (pr-1492 / main):

byte[] tempInput = new byte[input.length - inputOffset];
System.arraycopy(input, inputOffset, tempInput, 0, input.length - inputOffset);
rc = nativeInterface.do_CCM_encrypt(..., tempInput, tempInput.length, ...);

After:

byte[] tempInput = new byte[inputLen];
System.arraycopy(input, inputOffset, tempInput, 0, inputLen);
rc = nativeInterface.do_CCM_encrypt(..., tempInput, inputLen, ...);

Why the original is wrong (OpenSSL path only): On OCK, CCMHardwareFunctionPtr != -1 so the FastJNI/hardware branch above is always taken — this else block is dead code for OCK, which is why testDoFinalEncryptWithInputSlice passes in pr-1492 with the OCK backend. On OpenSSL, CCMHardwareFunctionPtr == -1 so this else block is the only path. When a caller passes a sliced buffer — e.g. doFinal(input, 40, 10, output, 0) where input.length == 100 — the pr-1492 form sizes tempInput to 60 bytes and passes 60 to the native encrypt. The output buffer is sized for 10 + tagLen, but the native call tries to write 60 + tagLen bytes, causing a ShortBufferException. Reverting to the pr-1492 form causes testDoFinalEncryptWithInputSlice to fail on the OpenSSL backend.

Why it cannot move to the adapter: tempInput is created in CCMCipher before being passed to the adapter. The fix must be at the point of allocation.

✔ Keep in CCMCipher.java. Real bug in pr-1492 that affects both backends — candidate for upstreaming to main.
