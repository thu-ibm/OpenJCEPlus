1. JNI_OnLoad OpenSSLJNI.c bootstrap

Called by the JVM the moment the native library is loaded. Verifies the OpenSSL version and initialises the debug flag. Returns JNI_VERSION_1_8 on success or JNI_ERR to abort loading.

JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM* vm, void* reserved)

Special JNI hook — not declared in a Java class. The JVM calls this automatically when System.loadLibrary() runs. The return value tells the JVM which JNI version this library requires.

unsigned long opensslVersion = OpenSSL_version_num(); if (opensslVersion < 0x30000000L) { fprintf(stderr, "ERROR: OpenSSL 3.0.0 or later is required..."); return JNI_ERR; }

Version guard. This codebase uses OpenSSL 3.0+ APIs (EVP_MD_fetch, OSSL_LIB_CTX, EVP_RAND) that do not exist in OpenSSL 1.x. Returning JNI_ERR causes the JVM to throw UnsatisfiedLinkError immediately with a clear stderr message.

(*vm)->GetEnv(vm, (void**)&env, JNI_VERSION_1_8);

Obtains a JNIEnv* from the JavaVM*. JNI_OnLoad receives a JavaVM* (process-wide), not a thread-local JNIEnv*. This call gets the thread-local env needed to call Java methods for the debug property check below.

debugEnv = getenv("OPENSSL_DEBUG"); if (debugEnv != NULL && (strcmp(debugEnv, "1") == 0 || strcmp(debugEnv, "true") == 0)) { debug = 1; }

First debug check: environment variable. Fast and works even before JNI is fully set up. Sets the global debug flag that all native functions check before logging.

propName = (*env)->NewStringUTF(env, "jceplus.openssl.debug"); propVal = (*env)->CallStaticObjectMethod(env, sysCls, getProp, propName); if (strcmp(val, "1") == 0 || strcmp(val, "true") == 0) { debug = 1; }

Second debug check: JVM system property -Djceplus.openssl.debug=true. Allows enabling debug logging at JVM launch without changing the OS environment. Only runs if the env var didn't already enable it.

return JNI_VERSION_1_8;

Tells the JVM this library uses JNI 1.8. The JVM stores this and uses it for future GetEnv calls. Returning a version the JVM doesn't support would cause load failure.

2. GCM_init OpenSSLGCM.c high value

Configures an existing EVP_CIPHER_CTX for AES-GCM with a specific key, IV, direction (encrypt/decrypt), and tag length. Must be called before GCM_update or GCM_encryptFinal/GCM_decryptFinal.

if (!validateIntRange(env, tagLen, MIN_GCM_TAG_SIZE, MAX_GCM_TAG_SIZE, ...)) { return; }

GCM tags must be 4–16 bytes (NIST SP 800-38D). Validated here at init time rather than at final time so bad parameters are caught before any data is processed.

if (EVP_CIPHER_CTX_reset(ctx) != 1) { ... return; }

Resets the context to a clean slate. Critical when a context is reused across multiple encrypt/decrypt operations (the Java layer caches contexts for performance). Without this, state from a previous operation leaks into the new one.

EVP_CipherInit_ex(ctx, cipherCtx->cipher, NULL, NULL, NULL, encryptFlag);

First init call — sets the cipher algorithm and direction (encryptFlag: 1=encrypt, 0=decrypt) but intentionally passes NULL for key and IV. This two-phase init pattern is required when you need to change IV length before committing key material.

if (ivLen != DEFAULT_GCM_IV_LENGTH) { EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, ivLen, NULL); }

Sets a non-default IV length. GCM's default is 12 bytes (96 bits) — the only length that avoids an extra GHASH computation and is recommended by NIST. Any other length is valid but requires this explicit override before the key/IV are loaded.

EVP_CipherInit_ex(ctx, NULL, NULL, (unsigned char*)keyBytes, (unsigned char*)ivBytes, encryptFlag);

Second init call — loads the actual key and IV. Passing NULL for the cipher algorithm means "keep the one already set". This two-step pattern is the standard OpenSSL way to set IV length before providing key material.

cipherCtx->tagLen = tagLen; cleanupByteArrays(env, key, keyBytes, iv, ivBytes);

Stores tagLen in the context so it can be validated later at encryptFinal/decryptFinal time. Then releases both pinned Java arrays with JNI_ABORT — they were read-only input.

3. GCM_update OpenSSLGCM.c medium value

Streams a chunk of plaintext (encrypt) or ciphertext (decrypt) through the GCM cipher and optionally processes AAD. Returns the number of output bytes produced.

if (!processAADFromArray(env, ctx, aad, aadLen, functionName)) { return -1; }

AAD can be fed on any update call. Internally calls EVP_CipherUpdate with a NULL output pointer — OpenSSL recognises this as "authenticate this data but don't encrypt it". Must all be fed before any ciphertext/plaintext bytes.

if (outputOffset > INT_MAX - inputLen || outputOffset + inputLen > outputLength) { setPendingOpenSSLException(..., "Invalid parameters or integer overflow"); }

Integer overflow guard on the output bounds check. If outputOffset is large, the addition outputOffset + inputLen could silently wrap to a small positive number and pass the array-length check — allowing a write past the end of the array. The INT_MAX - inputLen pre-check prevents that.

if (EVP_CipherUpdate(ctx, outputBytes + outputOffset, &outLen, inputBytes + inputOffset, inputLen) != 1) { ... } cleanupIOArrays(env, input, inputBytes, output, outputBytes, JNI_TRUE);

The actual encrypt/decrypt of this chunk. In GCM (CTR-mode) each byte of output corresponds to exactly one byte of input — outLen will equal inputLen. The output array is released with JNI_TRUE (commit) because we wrote to it; the input array is released with JNI_ABORT (read-only).

4. GCM_encryptFinal OpenSSLGCM.c high value

Final step of GCM encryption. Encrypts any remaining plaintext, flushes the cipher, and appends the authentication tag. Returns total bytes written (ciphertext + tag), or -1 on error.

if ((jlong)inputLen + (jlong)tagLen > (jlong)INT_MAX) { ... } requiredOutputSize = inputLen + tagLen;

Overflow guard — widening to jlong before adding prevents the sum from silently wrapping when inputLen is near INT_MAX. The output must hold ciphertext (same size as plaintext) plus the tag appended at the end.

EVP_CipherFinal_ex(ctx, outputBytes + outputOffset + totalOutLen, &finalLen);

In GCM (a stream mode), this typically produces 0 extra bytes — but it finalises the internal GHASH state. Must be called before EVP_CTRL_GCM_GET_TAG or the tag will be wrong/zeroed.

totalOutLen = getAndAppendTag(env, ctx, outputBytes, outputOffset, totalOutLen, tagLen, EVP_CTRL_GCM_GET_TAG, functionName);

The GCM-specific step. Calls EVP_CIPHER_CTX_ctrl(EVP_CTRL_GCM_GET_TAG) to extract the GHASH-computed tag, then appends it immediately after the ciphertext in the output buffer. The caller gets: [ciphertext][tag].

(*env)->ReleaseByteArrayElements(env, output, outputBytes, 0);

Mode 0 = commit. This is what makes the ciphertext + tag visible to Java. All previous array releases used JNI_ABORT (read-only). Only the output array needs a commit.

Output layout:  [ ciphertext (inputLen bytes) ][ tag (tagLen bytes) ] starting at outputOffset.

5. GCM_decryptFinal OpenSSLGCM.c high value

Final step of GCM decryption. The critical difference from encryptFinal: the tag is read from the end of the input, set for verification, and EVP_CipherFinal_ex either succeeds (tag matches) or fails (tag mismatch — data tampered). Plaintext is only committed on success.

if (inputLen < tagLen) { setPendingOpenSSLException(..., "GCM decrypt: inputLen is less than tagLen"); return -1; }

Safety check before computing requiredOutputSize = inputLen - tagLen. Without this, a negative result passed to validateOutputBuffer as a jint would wrap to a large positive number and pass the bounds check — a potential buffer overwrite.

unsigned char* tag = (unsigned char*)(inputBytes + inputOffset + inputLen - tagLen); EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_TAG, tagLen, tag);

Reads the tag from the last tagLen bytes of the input (the input layout is [ciphertext][tag]). Hands it to OpenSSL before processing the ciphertext so OpenSSL can compare it against its own GHASH computation during EVP_CipherFinal_ex.

EVP_CipherUpdate(ctx, outputBytes + outputOffset, &outLen, inputBytes + inputOffset, actualInputLen);

Decrypts only the ciphertext portion (inputLen - tagLen bytes). The tag bytes at the end are not fed through CipherUpdate — they were already extracted above.

if (!processZeroLengthInput(...)) { ... }

Special case for zero-length ciphertext. OpenSSL's GCM needs at least one CipherUpdate call to finalise its GHASH state even if there are no data bytes. The helper calls EVP_CipherUpdate with a zero-length buffer to trigger this.

if (EVP_CipherFinal_ex(ctx, ..., &finalLen) != 1) { ReleaseByteArrayElements(env, output, outputBytes, JNI_ABORT); setPendingOpenSSLException(env, OPENSSL_CIPHER_TAG_MISMATCH, ...); return OPENSSL_TAG_MISMATCH_ERROR; }

This is where GCM authentication actually happens. OpenSSL computes GHASH over all processed AAD + ciphertext and compares it against the tag set via EVP_CTRL_GCM_SET_TAG. If they differ, this returns failure. Critically, the output array is released with JNI_ABORT — the decrypted plaintext bytes are discarded, never returned to Java.

(*env)->ReleaseByteArrayElements(env, output, outputBytes, 0);

Only reached if tag verification passed. Commits the plaintext to the Java heap. The security property is: plaintext is never visible to Java unless the tag is valid.

Security note: The tag must be set with EVP_CTRL_GCM_SET_TAG before EVP_CipherFinal_ex, not after. Getting this order wrong causes OpenSSL to silently succeed regardless of the tag value.

6. EXTRAND_create OpenSSLRandom.c high value

Creates and instantiates a new HASH-DRBG context backed by the specified digest. Returns a jlong pointer to a heap-allocated DRBG_Context. This is the most complex Random function — failure here means SecureRandom is unavailable.

typedef struct { EVP_RAND_CTX *ctx; char *algName; } DRBG_Context;

The wrapper struct that C owns and Java holds as a jlong pointer. ctx is the OpenSSL EVP DRBG handle. algName is stored for diagnostics/future use.

if (strcmp(algNameChars, "SHA256") == 0) { digestName = "SHA-256"; } else if (strcmp(algNameChars, "SHA512") == 0) { digestName = "SHA-512"; }

Java passes "SHA256" / "SHA512" (no hyphen). OpenSSL's HASH-DRBG requires the EVP digest name format with a hyphen: "SHA-256", "SHA-512". This mapping bridges the naming gap.

rand = EVP_RAND_fetch(context->libctx, "HASH-DRBG", NULL); ... ctx = EVP_RAND_CTX_new(rand, NULL); EVP_RAND_free(rand);

Two-step OpenSSL 3 pattern. EVP_RAND_fetch looks up the HASH-DRBG algorithm from the provider. EVP_RAND_CTX_new creates an instance. The algorithm descriptor rand is then freed immediately — the context ctx holds its own internal reference.

OSSL_PARAM params[2]; params[0] = OSSL_PARAM_construct_utf8_string("digest", (char*)digestName, 0); params[1] = OSSL_PARAM_construct_end(); if (!EVP_RAND_instantiate(ctx, 0, 0, NULL, 0, params)) { ... }

Instantiates the DRBG — this is where OpenSSL seeds it from OS entropy (e.g. getrandom() / BCryptGenRandom) and starts the DRBG state machine. The params array specifies the underlying hash algorithm. Must be done at instantiation time, not after — OpenSSL's EVP_RAND design does not allow changing parameters on an already-running DRBG.

drbgCtx = malloc(sizeof(DRBG_Context)); storedAlgName = strdup(algNameChars); drbgCtx->ctx = ctx; drbgCtx->algName = storedAlgName; return (jlong)(intptr_t)drbgCtx;

Allocates the wrapper struct and stores both the live DRBG context and a copy of the algorithm name. Returns the pointer cast to jlong — Java stores this as an opaque handle. If either allocation fails the already-created EVP_RAND_CTX is freed before returning 0.

7. EXTRAND_setSeed OpenSSLRandom.c high value

Mixes caller-supplied entropy into an existing DRBG context. Backs SecureRandom.setSeed().

DRBG_Context *drbgCtx = (DRBG_Context *)(intptr_t)drbgContextId;

Recovers the C pointer from the Java jlong. The intptr_t intermediate cast suppresses 64-bit pointer-size warnings.

if (drbgCtx == NULL || drbgCtx->ctx == NULL) { ThrowNew(env, IllegalStateException, "DRBG context is null or invalid"); }

Guards against calling setSeed before create or after delete. Unlike other errors this is a programming mistake, hence IllegalStateException.

EVP_RAND_reseed(drbgCtx->ctx, 0, NULL, 0, (const unsigned char*)seedNative, (size_t)seedLen)

Mixes entropy into the DRBG without reinitialising it. The 0, NULL, 0 arguments disable prediction-resistance and suppress OpenSSL's own additional entropy sourcing — only the caller's bytes are mixed in. The DRBG continues generating from its updated state.

(*env)->ReleaseByteArrayElements(env, seed, seedNative, JNI_ABORT);

JNI_ABORT on both success and failure paths — we only read the seed, never wrote to the Java array, so no writeback is needed.

8. CCM_init OpenSSLCCM.c high value

Configures an EVP_CIPHER_CTX for AES-CCM. Critically different from GCM init: the tag length must be declared at init time via EVP_CTRL_CCM_SET_TAG, before any data is processed.

if (tagLen % 2 != 0) { setPendingOpenSSLException(..., "Invalid CCM tag length: must be even"); }

CCM tag lengths are constrained by NIST SP 800-38C to 4, 6, 8, 10, 12, 14, or 16 bytes (even values only). GCM allows any integer 4–16. This CCM-specific validation catches odd values that GCM would accept.

EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_CCM_SET_IVLEN, ivLen, NULL); EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_CCM_SET_TAG, tagLen, NULL);

The two CCM-mandatory setup calls before the key/IV are loaded. IV length must be 7–13 bytes (narrower than GCM). The EVP_CTRL_CCM_SET_TAG with a NULL data pointer means "I am telling you the tag size, not providing the tag" — for decryption the actual tag bytes come later via a second SET_TAG call with non-NULL data.

cipherCtx->tagLen = tagLen; cipherCtx->updateCount = 0;

Stores tag length (verified at final time) and resets the update counter. CCM only allows a single CipherUpdate call per operation — the counter enforces this.

GCM vs CCM init: GCM sets IV length only if non-default. CCM always must set both IV length and tag length before loading key/IV — OpenSSL has no defaults for CCM.

9. CCM_update OpenSSLCCM.c medium value

Processes plaintext/ciphertext through CCM. Has a fundamental difference from GCM_update: CCM requires the total plaintext length to be declared upfront, and only one data update call is permitted per operation.

if (cipherCtx->updateCount > 0) { setPendingOpenSSLException(..., "CCM_update called more than once per operation"); return -1; } cipherCtx->updateCount++;

CCM's CBC-MAC authentication is computed over the entire message in one pass. OpenSSL's CCM implementation allows only one EVP_CipherUpdate call for data — a second call re-announces the length and silently corrupts the authentication tag. This guard turns silent corruption into an explicit exception.

EVP_CipherUpdate(ctx, NULL, &outLen, NULL, inputLen);

The CCM "length announcement". Passing both output and input as NULL is a special OpenSSL CCM signal: "the plaintext will be inputLen bytes". This must be done before AAD is fed, because the CBC-MAC construction encodes the plaintext length in its first block. GCM does not have this requirement.

processAADFromArray(env, ctx, aad, aadLen, functionName); // ...then... EVP_CipherUpdate(ctx, outputBytes + outputOffset, &outLen, inputBytes + inputOffset, inputLen);

Order is mandatory: length announcement → AAD → ciphertext. Deviating from this order in CCM produces wrong tags or OpenSSL errors. GCM is more flexible about ordering.

10. CCM_decryptFinal OpenSSLCCM.c high value

Finalises CCM decryption with tag verification. Like GCM_decryptFinal but with CCM-specific constraints: tag length must match the value declared at CCM_init, and the length announcement pattern applies again.

if (tagLen != cipherCtx->tagLen) { setPendingOpenSSLException(..., "CCM tagLen mismatch: decryptFinal tagLen differs from CCM_init tagLen"); }

CCM's CBC-MAC is baked in at init time using the exact tag length declared then. Passing a different tag length at final time would mean verifying against a differently-computed MAC — a silently wrong result. GCM allows the tag length to vary call-to-call; CCM does not.

EVP_CipherUpdate(ctx, NULL, &outLen, NULL, actualInputLen);

CCM length announcement again — this time for the ciphertext length (same as plaintext length for decryption). Required even in decryptFinal because the CBC-MAC verification needs to know the message length before any AAD or data is processed.

extractAndSetTag(env, ctx, input, inputOffset, inputLen, tagLen, EVP_CTRL_CCM_SET_TAG, functionName);

Reads the tag from the last tagLen bytes of the input buffer and registers it with OpenSSL via EVP_CTRL_CCM_SET_TAG with non-NULL data. Must be done before the ciphertext CipherUpdate — CCM verifies inline during the update, not at final time like GCM.

if (EVP_CipherFinal_ex(...) != 1) { ReleaseByteArrayElements(env, output, outputBytes, JNI_ABORT); setPendingOpenSSLException(env, OPENSSL_CIPHER_TAG_MISMATCH, ...); return OPENSSL_TAG_MISMATCH_ERROR; }

Tag mismatch path — same as GCM: output released with JNI_ABORT, plaintext discarded. For CCM, OpenSSL can also report mismatch during EVP_CipherUpdate rather than waiting for final; the final call is still required to flush state.

CCM vs GCM tag verification timing: GCM verifies at EVP_CipherFinal_ex. CCM can fail earlier, during EVP_CipherUpdate, because CBC-MAC is computed inline. In both cases plaintext is discarded on failure.

11. CIPHER_create OpenSSLSymmetricCipher.c medium value

Allocates a CipherContext wrapper and fetches the named cipher algorithm from the OpenSSL provider. Separate from CIPHER_init — creation is done once, init is called each time key/IV change.

cipherCtx->ctx = createCipherCtxSafe(...);

Allocates an EVP_CIPHER_CTX — the OpenSSL state machine for a single cipher operation. It is kept alive across multiple init → update → final cycles via EVP_CIPHER_CTX_reset.

cipherCtx->cipher = EVP_CIPHER_fetch(context->libctx, name, NULL);

The OpenSSL 3 way to get a cipher. EVP_CIPHER_fetch looks up the algorithm by name (e.g. "AES-128-CBC") in the provider registered to context->libctx, returning an algorithm descriptor. This descriptor is reused across all operations on this context — it is not per-operation.

return (jlong)cipherCtx;

Returns the CipherContext* cast to jlong. Java stores this as the cipherId passed to every subsequent call. The Java layer is responsible for calling CIPHER_delete to free it.

12. CIPHER_init OpenSSLSymmetricCipher.c medium value

Loads key and IV into an existing cipher context and initialises it for encrypt or decrypt. Also securely copies key/IV into the context struct for potential re-init.

if (cipherCtx->key != NULL) { memset(cipherCtx->key, 0, cipherCtx->keyLen); free(cipherCtx->key); }

Zeroes the previous key before freeing. Without memset, key material would remain in heap memory until overwritten by the allocator — a security best practice for cryptographic material.

cipherCtx->key = mallocSafe(env, keyLen, ...); memcpy(cipherCtx->key, keyBytes, keyLen);

Makes a private copy of the key in the context. This allows CIPHER_init to be called again with the same key (e.g. to change direction or IV) without requiring Java to re-pass the key each time.

if (encrypt) { result = EVP_EncryptInit_ex(cipherCtx->ctx, cipherCtx->cipher, NULL, keyBytes, ivBytes); } else { result = EVP_DecryptInit_ex(cipherCtx->ctx, cipherCtx->cipher, NULL, keyBytes, ivBytes); }

Symmetric cipher uses explicit EVP_EncryptInit_ex / EVP_DecryptInit_ex rather than the unified EVP_CipherInit_ex used by GCM/CCM. The distinction matters for padding: CBC decrypt uses PKCS#7 padding verification in EVP_DecryptFinal_ex, which is only enabled on the decrypt path.

memset(keyBytes, 0, keyLen); cleanupByteArray(env, key, keyBytes, JNI_ABORT);

Zeroes the JNI-pinned copy of the key before releasing it. Even though JNI_ABORT discards changes back to the Java array, zeroing the native buffer prevents key material from lingering in C stack/heap memory.

13. KEYWRAP_wrap / KEYWRAP_unwrap OpenSSLKeyWrap.c medium value

AES Key Wrap (RFC 3394) and AES Key Wrap with Padding (RFC 5649). Encrypts a cryptographic key using another key (the KEK — Key Encryption Key). Returns the wrapped key as a new Java byte array.

static const EVP_CIPHER* getKeyWrapCipher(OSSL_LIB_CTX* libctx, int keyBits, jboolean padding) { const char* cipherName = padding ? "id-aes128-wrap-pad" : "id-aes128-wrap"; return EVP_CIPHER_fetch(libctx, cipherName, NULL); }

Selects between RFC 3394 (id-aes*-wrap) and RFC 5649 (id-aes*-wrap-pad) based on the padding flag. RFC 3394 requires the key being wrapped to be a multiple of 8 bytes. RFC 5649 adds padding to support any length — needed for keys like 24-byte 3DES.

EVP_EncryptInit_ex(ctx, cipher, NULL, kekNative, NULL);

The KEK is used as the encryption key. The IV is NULL — AES Key Wrap uses a fixed integrity check value (0xA6A6A6A6A6A6A6A6) as its IV; OpenSSL handles this internally.

int maxOutputLen = plaintextLen + AES_BLOCK_SIZE; outputNative = mallocSafe(env, maxOutputLen, "output buffer");

RFC 3394 wrapping adds exactly 8 bytes of overhead (one 64-bit integrity block). Allocating plaintextLen + 16 gives a safe upper bound for both RFC 3394 and RFC 5649.

EVP_EncryptUpdate(ctx, outputNative, &outputLen, plaintextNative, plaintextLen); EVP_EncryptFinal_ex(ctx, outputNative + outputLen, &finalLen); totalLen = outputLen + finalLen;

Standard update + final pattern, same as any EVP cipher. For key wrap, CipherUpdate performs the actual wrapping and EncryptFinal_ex flushes any remaining state. Unlike GCM/CCM there is no separate tag — integrity is embedded in the wrapped output by the RFC 3394 algorithm itself.

outputArray = newByteArraySafe(env, totalLen, functionName); (*env)->SetByteArrayRegion(env, outputArray, 0, totalLen, (jbyte*)outputNative);

Key wrap uses a different pattern from GCM/CCM: a fresh Java byte array is created and the result is copied into it with SetByteArrayRegion, rather than pinning a pre-existing output array. This is because the wrapped key length (an output of the operation) is not known to Java ahead of time.

// KEYWRAP_unwrap — decryption path: if (EVP_DecryptFinal_ex(ctx, outputNative + outputLen, &finalLen) != 1) { setPendingOpenSSLException(env, OPENSSL_CIPHER_FINAL_FAILED, "EVP_DecryptFinal_ex failed for key unwrap - integrity check failed"); }

For unwrap, DecryptFinal_ex failing means the integrity check embedded in the RFC 3394 format failed — the wrapped key was corrupted or the wrong KEK was used. The error message explicitly says "integrity check failed" to distinguish this from a generic cipher failure.

Key wrap vs AES-GCM: Both protect keys, but serve different purposes. GCM is a general-purpose AEAD cipher. RFC 3394 Key Wrap is specifically designed for key material — it has no IV (eliminating IV-reuse risk) and its output length is deterministic.
