Root Cause (single): NativeOpenSSLImplementation.java tries to load libopenjceplus_64.dll on Windows — but the actual DLL built is named libjgskit_openssl_64.dll. This causes ExceptionInInitializerError on the very first test, which cascades to NoClassDefFoundError on every subsequent test in the JVM.

Problem 1 — Wrong DLL name in preloadOpenJCEPlusNative() Critical

File

src/main/java/com/ibm/crypto/plus/provider/openssl/NativeOpenSSLImplementation.java

Symptom

java.security.ProviderException: Could not load dependent openjceplus library
  for os.name=Windows 11, os.arch=amd64
  at NativeOpenSSLImplementation.preloadOpenJCEPlusNative(NativeOpenSSLImplementation.java:156)

Root Cause in pr-1492

The constant name and the resulting filename do not match the DLL that is actually built by the makefile:

- private static final String OPENJCEPLUS_CORE_LIBRARY_NAME = "openjceplus";
-   // on Windows builds: "lib" + "openjceplus" + "_64.dll" → libopenjceplus_64.dll  ← DOES NOT EXIST

Solution from openssl-aes

The working branch uses JGSKIT_LIBRARY_NAME = "libjgskit_openssl_64" with a dedicated preloadJGskit() method that directly appends .dll (no extra lib prefix, because the full prefix is already part of the name):

+ private static final String JGSKIT_LIBRARY_NAME = "libjgskit_openssl_64";
+
+ static void preloadJGskit() {
+     String jgskitPath = getJGskitLoadPath();
+     File jgskitFile = getLibraryFile(jgskitPath, JGSKIT_LIBRARY_NAME);
+     //  getLibraryFile() appends .dll / .so / .dylib
+     boolean loaded = loadIfExists(jgskitFile);
+     if (!loaded) throw new ProviderException("Could not load " + JGSKIT_LIBRARY_NAME + " ...");
+ }

Load path resolution (openssl-aes)

getJGskitLoadPath() checks in priority order:

  1. -Djgskit.library.path system property
  2. -Dopenssl.library.path system property
  3. %JAVA_HOME%\bin (Windows) or $JAVA_HOME/lib (Linux/Mac) — fallback

Problem 2 — OpenSSL preload uses wrong filename on Windows Critical

File

src/main/java/com/ibm/crypto/plus/provider/openssl/NativeOpenSSLImplementation.java

Root Cause in pr-1492

getOSSLLoadFile() on the Java home fallback path constructs crypto-semeru.dll (no lib prefix) — which doesn't exist on a standard OpenSSL install:

-  loadFile = new File(osslPath, OPENSSL_CORE_LIBRARY_NAME + "-semeru.dll");
-  // → "crypto-semeru.dll"  ← does not exist anywhere

Solution from openssl-aes

The working branch uses two named constants that match actual OpenSSL 3 filenames and reads OPENSSL_HOME\bin first via env var:

+ private static final String OPENSSL_LIBRARY_NAME = "libssl-3-x64";
+ private static final String CRYPTO_LIBRARY_NAME  = "libcrypto-3-x64";
+
+ static void preloadOpenSSL() {
+     String opensslPath = getOpenSSLLoadPath();  // checks OPENSSL_HOME\bin first
+     File cryptoFile = getLibraryFile(opensslPath, CRYPTO_LIBRARY_NAME);
+     File sslFile    = getLibraryFile(opensslPath, OPENSSL_LIBRARY_NAME);
+     boolean cryptoLoaded = loadIfExists(cryptoFile);
+     boolean sslLoaded    = loadIfExists(sslFile);
+     if (!cryptoLoaded || !sslLoaded)
+         throw new ProviderException("Could not load OpenSSL libraries ...");
+ }

getOpenSSLLoadPath() priority order: OPENSSL_HOME env var → openssl.library.path property → JAVA_HOME\bin.

Problem 3 — NativeImplementation.java base class not present in openssl-aes Architecture diff

File

src/main/java/com/ibm/crypto/plus/provider/base/NativeImplementation.java (new in pr-1492)

Situation

pr-1492 introduces a new abstract base class NativeImplementation that holds the shared loadIfExists() logic. NativeOpenSSLImplementation extends NativeImplementation. This class does not exist in openssl-aes — the working branch keeps loadIfExists() as a private static method directly inside NativeOpenSSLImplementation.

The base class itself is correct; the breakage is not here — it is in Problems 1 & 2 above. However, if only the library loading methods from openssl-aes are ported back, the extends NativeImplementation relationship must be kept consistent (either keep the base class and fix the library names, or revert to the self-contained approach from openssl-aes).

Recommended Fix Strategy

  1. Option A — Cherry-pick openssl-aes Java files: Run git checkout openssl-aes -- src/main/java/com/ibm/crypto/plus/provider/openssl/ (and other differing dirs) to replace all broken Java with the known-working versions. Same as was done for the native C/H files.
  2. Option B — Targeted fix: In NativeOpenSSLImplementation.java, change OPENJCEPLUS_CORE_LIBRARY_NAME = "openjceplus" → JGSKIT_LIBRARY_NAME = "libjgskit_openssl_64", restore preloadJGskit(), restore correct OpenSSL preload using libssl-3-x64 / libcrypto-3-x64, and restore VALUE_OPENSSL_VERSION/VALUE_OPENSSL_INSTALL_PATH ordering in the adapter.

Option A is safer given the number of differing files (27 Java files total). Option B is suitable if only the loader fix is desired and the rest of pr-1492's changes are intentional.
