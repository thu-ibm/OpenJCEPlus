NativeOpenSSLAdapter.java
1 NativeOpenSSLAdapter.java
OpenSSL context never initialised
initializeContext() has long osslContextId = 0; — the actual NativeOpenSSLImplementation.initializeOSSL() call is commented out. Every JNI call runs against context ID 0 (NULL).
✓ Superseded — ojp_master calls initializeOpenSSL(fipsMode) and stores the real context.
 High Superseded
2 NativeOpenSSLAdapter.java
All AES/GCM/CCM/KeyWrap methods are stubs
Every cipher method returns null or throws UnsupportedOperationException. The PR has no working AES implementation at all.
✓ Superseded — ojp_master wires all methods to real JNI calls.
 High Superseded
3 NativeOpenSSLAdapter.java
Non-thread-safe singleton — missing volatile
NativeOpenSSLAdapterNonFIPS.instance is not volatile. Under the Java memory model, a second thread can see a partially-constructed instance without the double-checked locking guard.
✓ Superseded — ojp_master uses volatile on the instance field.
 High Superseded
4 NativeOpenSSLAdapter.java
validateOSSLLocation = true causes startup failure in all test environments
The flag is hardcoded true, but the validation path throws if the library path isn't exactly as expected — which it never is in a dev/CI environment.
✓ Superseded — ojp_master defaults to false, opt-in via system property.
 High Superseded
5 NativeOpenSSLAdapter.java
HKDF uses HKDF_DUMMY_CONTEXT_ID = 1L
A hardcoded dummy long 1L is passed as context ID to HKDF JNI calls. If any real context happens to have ID 1, this collides silently.
✓ Superseded — ojp_master passes the real opensslContext.getId().
 Medium Superseded
6 NativeOpenSSLAdapter.java
EC key store: AtomicLong counter has no wraparound guard
The in-memory EC key store uses an AtomicLong counter as fake key IDs. At Long.MAX_VALUE it wraps to a negative value, silently colliding with an existing key entry.
 Low Superseded
7 NativeOpenSSLAdapter.java
ThreadLocal for HKDF digest algorithm — potential memory leak
A ThreadLocal<String> is set in some HKDF methods but never removed via remove(), leaking the reference in thread pool environments.
 Low Superseded

OpenSSL 3.x on Windows ships as libcrypto-3-x64.dll. PR#1492 constructs new File(osslPath, OPENSSL_CORE_LIBRARY_NAME + ".dll") → crypto.dll, which does not exist. Library load fails silently or throws.

✓ Superseded — ojp_master uses consistent initializeOpenSSL on both sides.
