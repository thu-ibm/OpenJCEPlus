1. Project Context

OpenJCEPlus is IBM's JCE provider backed by the GSKit/ICC (OCK) native library. pr-1492 introduces a second native backend: OpenSSL 3.x — initially scoped to AES symmetric cipher (ECB/CBC/CTR/OFB/CFB), AES-GCM, AES-CCM, AES Key Wrap, and SecureRandom (HASHDRBG).

Two parallel branches exist:

  • openssl-aes — IBM-internal proof-of-concept (295 AES tests, all passing)
  • pr-1492 — the merge target for the public IBM/OpenJCEPlus repository, which has a newer API surface requiring integration work

The goal of this work is to bring pr-1492 to feature parity with openssl-aes and validate it with the full TestOpenJCEPlus suite filtered to the OpenJCEPlus_OpenSSL tag.

2. Architecture Overview

Java test (e.g. TestAESGCMUpdate)
  │  loadProviderOpenSSL() → "OpenJCEPlus-OpenSSL" (OpenSSLOnly.config)
  │  Cipher.getInstance("AES/GCM/NoPadding", "OpenJCEPlus-OpenSSL")
  ▼
AESGCMCipher ──── NativeCryptoSelector.selectBackend(provider, "Cipher", "AES/GCM/NoPadding")
                        reads NativeProvider attribute = "OpenSSL"
                        └─► NativeOpenSSLAdapterNonFIPS.getInstance()
                                  │
                                  ▼ JNI
                         libjgskit_openssl_64.dll
                         OpenSSLGCM.c / OpenSSLCCM.c / OpenSSLSymmetricCipher.c
                                  │
                                  ▼
                         OpenSSL 3.x EVP API
                         (libcrypto-3-x64.dll from C:\OpenSSL-v3)

Key selector rule: NativeCryptoSelector reads the NativeProvider service attribute. Value "OpenSSL" → NativeOpenSSLAdapterNonFIPS. Missing/blank/other → OCK. This is set per-service in the config file.

5. pr-1492 Session Changes (2026-08-17): 10 AES Tests to PASS

FIX create_GCM_context(int keySize) overload 2026-08-17 NativeInterface.java, NativeOCKAdapter.java, NativeOpenSSLAdapter.java

GCMCipher.java calls create_GCM_context(int keySize) but NativeInterface only had the no-arg overload. Compile error: "method create_GCM_context cannot be applied to given types".

  • NativeInterface.java: added long create_GCM_context(int keySize) throws NativeException;
  • NativeOCKAdapter.java: ignores keySize, delegates to no-arg (OCK resolves cipher from key at init time)
  • NativeOpenSSLAdapter.java: maps keySize to cipher name (16→AES-128-GCM, 24→AES-192-GCM, 32→AES-256-GCM) then calls CIPHER_create
Why the overload matters for OpenSSL: OpenSSL's EVP API requires the cipher algorithm to be named at context creation time (e.g. EVP_aes_256_gcm()). Providing key size at creation lets the adapter select the correct EVP cipher immediately.
FIX OpenSSLException(String, int) constructor missing — NoSuchMethodError at runtime 2026-08-17 OpenSSLException.java

The native DLL constructs OpenSSLException via JNI as new OpenSSLException(message, errorCode). The pr-1492 stub only had (String), (String, Throwable), and (int) constructors.

Fix: Replaced with the openssl-aes version which adds the (String, int) constructor, full error-code constants, getErrorCodeString(int), and a toString() override.

FIX AESGCMCipher: post-doFinal state guards (OpenSSL backend) 2026-08-17 AESGCMCipher.java

The cipher allowed updateAAD() after doFinal() without re-init, violating the JCE GCM contract. Added finalCalled / singleShotFinalCalled fields (ported from openssl-aes) with guards in engineUpdateAAD and engineDoFinal.

Why OpenSSL-only guards: OCK enforces these constraints internally via requireReinit/checkReinit. OpenSSL's EVP context is stateless between calls — the Java layer must enforce the JCE contract explicitly.
FIX engineUpdateAAD: successive calls must concatenate, not replace, AAD 2026-08-17 AESGCMCipher.java

Previous implementation allocated a fresh authData array on each call, silently discarding prior AAD. Fixed: both engineUpdateAAD overloads now check authData != null and append old + new data into a combined array.

FIX Short GCM tag (2 bytes) rejected by native MIN_GCM_TAG_SIZE = 4 2026-08-17 NativeOpenSSLAdapter.java

TestAESGCMBufferIV passes new GCMParameterSpec(16, iv) (16 bits = 2 bytes tag). The native enforces a 4-byte minimum. Fix: compute nativeTagLen = Math.max(tagLen, 4) in do_GCM_encrypt/decrypt; only tagLen bytes are returned to / consumed from the caller.

Rationale: NIST SP 800-38D permits 4–16 byte tags; OpenSSL 3.x EVP enforces 4-byte minimum at EVP_CIPHER_CTX_ctrl(EVP_CTRL_GCM_SET_TAG). Clamping in the Java adapter bridges this without changing C code or the caller-visible tag bytes.
INFRA Removed all [AES-TRACE] debug printf/fflush statements from native C 2026-08-17 OpenSSLSymmetricCipher.c, OpenSSLGCM.c, OpenSSLCCM.c

Removed 2 trace pairs from OpenSSLSymmetricCipher.c, 1 from OpenSSLGCM.c, 1 from OpenSSLCCM.c. DLL rebuilt via buildNativeOpenSSL_Win64_AutoEnv.bat.

6. Broader Suite Run — Initial Analysis (2026-08-17)

After all 10 AES tests passed, the full run_suite_openssl.bat (tag OpenJCEPlus_OpenSSL) was run. Initial result: 441 tests, 2 failures, 144 errors. Two root causes found and fixed in this session.

FIX OpenSSLOnly.config / OCKOnly.config — name value mismatched TestProvider enum 2026-08-17 src/test/OpenSSLOnly.config, src/test/OCKOnly.config

144 errors — NoSuchProvider: OpenJCEPlus-OpenSSL across all digest test classes.

Root cause: Config files shipped with name = OpenSSL / name = OCK, but TestProvider.java expected "OpenJCEPlus-OpenSSL" / "OpenJCEPlus-OCK". OpenJCEPlus.configure() calls super(config.getName(), …), so the provider is registered under the name exactly as written. Security.getProvider("OpenJCEPlus-OpenSSL") always returned null.

Fix: Set name = OpenJCEPlus-OpenSSL and name = OpenJCEPlus-OCK.

Design Decision: The name field must match the first argument of the TestProvider enum entry verbatim. The "OpenJCEPlus-*" pattern is conventional for JCE provider name variants of a base provider.
FIX OpenSSLOnly.config — merged AES Cipher + SecureRandom entries 2026-08-17 src/test/OpenSSLOnly.config

Once the provider name was corrected, the parameterised AES tests (which run against "OpenJCEPlus-OpenSSL") found no AES or SecureRandom services. Added the full AES Cipher + SecureRandom section from ProviderOpenSSLAttrs.config into OpenSSLOnly.config.

Two config files — two different code paths:
  • OpenSSLOnly.config → name OpenJCEPlus-OpenSSL — used by BaseTest.loadProvider(OpenJCEPlus_OpenSSL) for all @Tag(OPENJCEPLUS_OPENSSL_NAME) parameterised tests.
  • ProviderOpenSSLAttrs.config → name OpenJCEPlus — used by BaseUtils.loadProviderOpenJCEPlus() when -Dopenjceplus.useOpenSSL=true. Used exclusively by legacy interop tests that hardcode provider name "OpenJCEPlus" in their test body.
These two paths are independent and cannot be merged — they produce providers with different names.

7. Suite Run — AES Test Provider Migration (2026-08-17 to 2026-08-18)

After the config name fix the suite ran at 428 tests, 0 failures, 11 errors, 2 skipped. This section documents the migration of 9 AES test classes to the canonical "OpenJCEPlus-OpenSSL" provider pattern.

TEST Migrated 9 AES test classes to loadProviderOpenSSL() + OPENSSL_PROVIDER_NAME 2026-08-17 TestAESGCMUpdate, TestAESGCMWithKeyAndIvCheck, TestAESGCMUpdateInteropBC, TestAESGCMBufferIV, TestAESGCM_ExtIV, TestAESGCM_IntIV, TestAESCCMInteropBC, TestAESCCMParameters, TestAESKeyWrap

Each @BeforeAll was updated from Utils.loadProviderTestSuite() + TEST_SUITE_PROVIDER_NAME to Utils.loadProviderOpenSSL() + OPENSSL_PROVIDER_NAME ("OpenJCEPlus-OpenSSL"), and the tag @Tag(Tags.OPENJCEPLUS_OPENSSL_NAME) was added where missing.

Why these 9 and not all 10: TestAES256Interop's base class (BaseTestAESInterop) hardcodes provider strings "OpenJCEPlus" and "SunJCE" in the test body — it never calls getProviderName(). Changing its provider registration has no effect. See §8.
INFRA Utils.java — added loadProviderOpenSSL(), OPENSSL_PROVIDER_NAME, OPENSSL_CONFIG 2026-08-17 src/test/java/ibm/jceplus/junit/openjceplus/Utils.java

New static method loadProviderOpenSSL(): calls new OpenJCEPlus().configure("./src/test/OpenSSLOnly.config") and inserts the result at security position 1 as "OpenJCEPlus-OpenSSL". The old loadProviderTestSuite() is retained but marked @Deprecated.

TEST OpenSSLOnly.config — full service declarations for all AES cipher, SecureRandom, KeyGenerator, AlgorithmParameters 2026-08-17 src/test/OpenSSLOnly.config

Added Service. lines for every service the 9 AES tests use under the "OpenJCEPlus-OpenSSL" provider. The ProviderServiceReader only registers services with an explicit Service.<Type>.<Algo> line — attr.add and alias.add lines alone do not register a service.

Each AES cipher service includes attr.add.NativeProvider = OpenSSL so NativeCryptoSelector routes them to the OpenSSL backend. All Key Wrap aliases (AESWrap, AESWrapPad, AESWrap_128, …) added to match DefaultProviderAttrs.java.

8. Suite Run — Final Fixes to Reach 441/0/0 (2026-08-18)

Final result: Tests run: 441, Failures: 0, Errors: 0, Skipped: 0
FIX TestAES256Interop — reverted to loadProviderTestSuite() + restored -Dopenjceplus.useOpenSSL=true 2026-08-18 TestAES256Interop.java, run_suite_openssl.bat

3 errors — ProviderException: SecureRandom not available in testAESOnlyFinal, testAESWithUpdateForEncryptionAndDecryption, and testAESWithUpdateForEncryptionButOnlyFinalForDecryption.

Root cause: BaseTestAESInterop hardcodes provider strings "OpenJCEPlus" and "SunJCE" directly in its test body methods (e.g. doTestAESOnlyFinal(..., "OpenJCEPlus", "SunJCE")) — bypassing getProviderName() entirely. When the test was changed to register "OpenJCEPlus-OpenSSL", the underlying calls still requested Cipher.getInstance(algo, "OpenJCEPlus"). This found the JVM-default "OpenJCEPlus" provider (loaded from java.security at JVM startup, before the OCK native path is properly initialised). That provider could not instantiate SecureRandom.SHA256DRBG, causing ProviderException: SecureRandom not available at cipher.init(ENCRYPT_MODE, key).

Comparison with original openssl-aes branch: In that branch, loadProviderTestSuite() loaded ProviderOpenSSLAttrs.config (default = true → all services including SecureRandom.SHA256DRBG, AES overridden to OpenSSL) and registered the result as "OpenJCEPlus" at position 1. The hardcoded "OpenJCEPlus" in the test body found exactly this provider — fully functional, AES routed to OpenSSL.

Fix:

  • Reverted TestAES256Interop.@BeforeAll to use Utils.loadProviderTestSuite() + setProviderName(Utils.TEST_SUITE_PROVIDER_NAME) — identical to the openssl-aes branch.
  • Restored -Dopenjceplus.useOpenSSL=true to run_suite_openssl.bat so that loadProviderTestSuite() → loadProviderOpenJCEPlus() loads ProviderOpenSSLAttrs.config (default = true) and registers "OpenJCEPlus" with all services + OpenSSL AES backend.
Design Decision — TestAES256Interop uses "OpenJCEPlus", not "OpenJCEPlus-OpenSSL": This test is an OCK↔SunJCE interoperability test. The @Tag(OPENJCEPLUS_OPENSSL_NAME) tag means it runs in the OpenSSL suite, but the provider it exercises is "OpenJCEPlus" (configured via ProviderOpenSSLAttrs.config to route AES to OpenSSL). The test validates that AES encrypted by our provider (OpenSSL backend) can be decrypted by SunJCE, and vice versa. The distinction between "OpenJCEPlus" and "OpenJCEPlus-OpenSSL" is a config-loading path detail, not a functional difference for AES operations.
FIX TestAESKeyWrap.testInvalidKeyAlgorithm aborted due to missing KeyGenerator.DESede 2026-08-18 src/test/OpenSSLOnly.config

2 aborted tests (JUnit 5 shows [??], not [XX]) in testInvalidKeyAlgorithm[1] AES_192/KW/NoPadding and [2] AES_192/KWP/NoPadding.

Root cause: The test calls createKey("DESede", 168, getProviderName()) to produce a key with the wrong algorithm, then expects cp.init(WRAP_MODE, wrongKey) to throw InvalidKeyException. Since DESede was not registered in OpenSSLOnly.config, KeyGenerator.getInstance("DESede", "OpenJCEPlus-OpenSSL") threw NoSuchAlgorithmException. The broad catch (Exception e) called assumeTrue(false) (JUnit 5 abort), so the test never reached the expected InvalidKeyException.

Fix: Added KeyGenerator.DESede (OCK backend — no NativeProvider attribute) to OpenSSLOnly.config:

KeyGenerator.DESede.alias.add = TripleDES, 3DES
Service.KeyGenerator.DESede = com.ibm.crypto.plus.provider.DESedeKeyGenerator

With this, createKey("DESede", …) succeeds (OCK generates the key), cp.init(WRAP_MODE, wrongKey) throws InvalidKeyException as expected, and the test passes.

Why OCK for DESede: DESede is not in scope for the OpenSSL backend — only AES is targeted. Registering it with OCK (by omitting NativeProvider) satisfies the test precondition without claiming OpenSSL support for DESede. The OpenJCEPlus-OpenSSL provider only routes explicitly listed OpenSSL services to the OpenSSL backend; everything else falls through to OCK.
