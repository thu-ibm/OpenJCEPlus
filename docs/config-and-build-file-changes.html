1 · pom.xml

Changed

1a — TestOpenJCEPlus excluded from default surefire run

pr-1492 ran the OpenSSL suite class TestOpenJCEPlus as part of the default test execution. This branch adds it to the surefire <excludes> list alongside the other suite classes that must be invoked explicitly:

+ **/ibm/jceplus/junit/suites/TestOpenJCEPlus.java,

Why: TestOpenJCEPlus requires -Djgskit.library.path pointing at the OpenSSL native library. Without that property the entire test suite errors out before any test runs. Excluding it from the default run prevents CI failures on machines that only have OCK configured. It is still included when explicitly requested with -Dtest=ibm.jceplus.junit.suites.TestOpenJCEPlus or via -Dgroups=OpenJCEPlus_OpenSSL.

1b — printStdoutOnSuccess / printStderrOnSuccess — unchanged (false)

These remain at the pr-1492 default of false in both the primary and performance-test surefire executions. No change is made in this branch.

2 · src/test/OpenSSLOnly.config

Changed

This file is the provider configuration loaded when running OpenSSL-backend tests. pr-1492 had only MessageDigest services configured; this branch expands it significantly.

2a — Provider name corrected

- name = OpenSSL
+ name = OpenJCEPlus-OpenSSL

Why: The name field becomes the provider name returned by Provider.getName() after the config is applied. Tests that call Cipher.getInstance("AES/GCM/NoPadding", "OpenJCEPlus-OpenSSL") require this exact string. The pr-1492 value "OpenSSL" caused NoSuchProviderException in all tests that looked up the provider by name.

2b — NativeProvider attribute value corrected

- MessageDigest.MD5.attr.add.NativeProvider = OPENSSL
+ MessageDigest.MD5.attr.add.NativeProvider = OpenSSL

Same fix applied to all 13 MessageDigest services. Why: The NativeCryptoSelector dispatches based on the value of this attribute; it compares against the string "OpenSSL" (case-sensitive). The all-caps "OPENSSL" in pr-1492 caused the selector to fall back to OCK for every digest operation even when the OpenSSL config was loaded.

2c — SecureRandom services added

+ Service.SecureRandom.SHA256DRBG = com.ibm.crypto.plus.provider.HASHDRBG$SHA256DRBG
+ SecureRandom.SHA256DRBG.alias.add = HASHDRBG, SHA2DRBG
+ SecureRandom.SHA256DRBG.attr.add.ThreadSafe = true
+ SecureRandom.SHA256DRBG.attr.add.NativeProvider = OpenSSL
+ (+ SHA512DRBG equivalents)

Why: AESCipher.engineInit generates a random IV using SecureRandom.getInstance(..., provider) when no IV is supplied. If SecureRandom is not registered under the OpenSSL provider, the getInstance call throws NoSuchAlgorithmException and every AES encrypt-without-IV test fails.

2d — KeyGenerator services added

+ Service.KeyGenerator.AES = com.ibm.crypto.plus.provider.AESKeyGenerator
+ Service.KeyGenerator.DESede = com.ibm.crypto.plus.provider.DESedeKeyGenerator

Why: Tests that call KeyGenerator.getInstance("AES", providerName) require the service to be registered under the OpenSSL provider. Without it they get NoSuchAlgorithmException before any cipher operation begins. DESede is needed specifically by the AES KeyWrap tests that verify an invalid key algorithm is rejected. Both implementations are pure Java — no native code required for either.

2e — AlgorithmParameters and AlgorithmParameterGenerator services added

+ Service.AlgorithmParameters.AES   = com.ibm.crypto.plus.provider.AESParameters
+ Service.AlgorithmParameters.GCM   = com.ibm.crypto.plus.provider.GCMParameters
+ Service.AlgorithmParameters.CCM   = com.ibm.crypto.plus.provider.CCMParameters
+ Service.AlgorithmParameterGenerator.GCM = ...
+ Service.AlgorithmParameterGenerator.CCM = ...

Why: AESCipher.engineGetParameters() calls AlgorithmParameters.getInstance("AES", provider). Similarly AESGCMCipher and AESCCMCipher use GCMParameters / CCMParameters. Without these registrations, Cipher.getParameters() would throw and a variety of GCM/CCM tests that check IV extraction would fail. All five implementations are pure Java — no native code required.

2f — AES Cipher services added

+ Cipher.AES.attr.add.NativeProvider = OpenSSL
+ Service.Cipher.AES = com.ibm.crypto.plus.provider.AESCipher

+ Cipher.AES/GCM/NoPadding.attr.add.NativeProvider = OpenSSL
+ Service.Cipher.AES/GCM/NoPadding = com.ibm.crypto.plus.provider.AESGCMCipher

+ Cipher.AES/CCM/NoPadding.attr.add.NativeProvider = OpenSSL
+ Service.Cipher.AES/CCM/NoPadding = com.ibm.crypto.plus.provider.AESCCMCipher

+ (+ 10 AES KeyWrap variants: KW/KWP x AES/AES_128/AES_192/AES_256/AESWrap)

Why: pr-1492's config registered only digests. Without explicit Cipher service registrations, Cipher.getInstance("AES/GCM/NoPadding", "OpenJCEPlus-OpenSSL") throws NoSuchAlgorithmException and every AES test fails. Each service registration also sets NativeProvider = OpenSSL so that NativeCryptoSelector dispatches to the OpenSSL adapter rather than OCK.

The KeyWrap variants cover all alias forms the tests reference: AESWrap, AESWrapPad, AESWrap_128, AESWrapPad_128, etc.

3 · src/test/OCKOnly.config

Changed

Provider name made unambiguous

- name = OCK
+ name = OpenJCEPlus-OCK

Why: With both OCKOnly.config and OpenSSLOnly.config active in the same JVM (e.g. when both providers are tested in one Maven run), the short name "OCK" is ambiguous — it does not match the provider name the tests look up ("OpenJCEPlus"). The fully-qualified name "OpenJCEPlus-OCK" is consistent with the pattern used by the OpenSSL config and avoids provider-lookup confusion.

4b — Windows (primary build entry point): openjceplus.win64.cygwin.mak

Changed (rewritten)

This file was fully rewritten as a self-contained, nmake-compatible makefile that builds all 10 OpenSSL objects directly into libjgskit_openssl_64.dll. It no longer delegates to common.win64.cygwin.mak via !INCLUDE. It is the Windows equivalent of jgskit.win64.cygwin.mak for OCK, and is called from buildNativeWin64.bat.

Why it was rewritten (not just amended)

The original file delegated to common.win64.cygwin.mak via !INCLUDE. That shared makefile contained GNU-make-only constructs (?= conditional assignment, ifneq/endif, order-only | prerequisites) which are not supported by nmake. This caused the build to stop after compiling only one object file. The rewrite replaces the delegation pattern with an inline, nmake-compatible ruleset, adding a headers target that runs javac -h to regenerate JNI header files before compilation.

Also fixed: common.win64.cygwin.mak

-I. was added to the .c.obj inference rule so that local header files in the OpenSSL source directory are found during compilation.

5 · openssl.win64.mak

Gitignored — dev-local standalone makefile

This file is not tracked in the repository. It has been added to .gitignore as a dev-local standalone makefile. The canonical Windows build entry point for the OpenSSL DLL is the rewritten openjceplus.win64.cygwin.mak (see §4b), which is called from buildNativeWin64.bat alongside the OCK makefile. openssl.win64.mak was retained locally during development as a standalone alternative but is superseded and no longer needed in the tracked tree.

6 · buildNativeWin64OpenSSL.bat

Gitignored — dev-local convenience script

This file is not tracked in the repository. It has been added to .gitignore as a dev-local convenience script. The canonical Windows build entry point for the OpenSSL DLL is buildNativeWin64.bat, which now calls openjceplus.win64.cygwin.mak (rewritten — see §4b).

Why gitignored

buildNativeWin64OpenSSL.bat was created during development as a standalone script that invoked openssl.win64.mak directly. With openjceplus.win64.cygwin.mak rewritten to be self-contained, the OpenSSL DLL is now built by buildNativeWin64.bat in the same pass as the OCK DLL — consistent with how OCK uses jgskit.win64.cygwin.mak. The standalone script is no longer needed in CI or as a tracked file. Local copies remain untracked for developer convenience.
