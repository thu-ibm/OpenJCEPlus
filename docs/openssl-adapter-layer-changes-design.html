OpenSSL Adapter Layer — Changes & Design

Branch thu/openssl-aes — NativeOpenSSLAdapter.java, NativeOpenSSLImplementation.java, native C sources

Legend: New added in this branch   Changed behaviour differs from OCK counterpart   No-op / pass-through delegates unchanged   Stub / UnsupportedOperation not yet ported

1 · Architecture Overview

The provider sits between the JCE layer and a native crypto library. The original backend was IBM OCK (ICC). The new OpenSSL backend keeps the same three-layer stack, replacing only the bottom two layers:

JCE provider layer — AESGCMCipher, GCMCipher, CCMCipher, …
↕ calls NativeInterface methods
NativeInterface (interface) — backend-agnostic contract; NativeOCKAdapter or NativeOpenSSLAdapter selected at runtime by NativeCryptoSelector
↕ calls static native methods
NativeOpenSSLImplementation — thin JNI bridge; every method prepends osslContextId and calls the C side
↕ JNI
libjgskit_openssl_64 — C code in src/main/native/openssl/; calls OpenSSL EVP API

NativeOpenSSLAdapter is abstract; the concrete subclass NativeOpenSSLAdapterNonFIPS selects FIPS/non-FIPS mode at construction time. The adapter holds one OpenSSLContext (a value object wrapping the native osslContextId long) and injects it as the first argument into every NativeOpenSSLImplementation call, mirroring how NativeOCKAdapter injects ockContextId.

2 · Initialization

New

Class-level constants and sentinels

Three fields use a lazy-fetch pattern with a sentinel object rather than null, because the fetched value itself might be null:

static final String unobtainedValue = new String(); // unique identity — never equals any real string

private String osslVersion      = unobtainedValue;  // per-instance: OpenSSL version string
private String osslInstallPath  = unobtainedValue;  // per-instance: path where libcrypto was found
private static String libraryBuildDate = unobtainedValue; // class-level: JNI DLL build date

Callers check == unobtainedValue (identity comparison) to decide whether to fetch. This avoids a second native call if the real value turns out to be null.

Two other constants used throughout the GCM methods:

private static final int   DEFAULT_GCM_TAG_LEN = 16;    // default tag length for update-path GCM_init
private static final byte[] EMPTY_BYTE_ARRAY   = new byte[0]; // reusable empty array for zero-data GCM_update calls

Library loading — NativeOpenSSLImplementation static initializer

Before any JNI call can be made, two native libraries must be loaded in order:

  • preloadOpenSSL() — resolves and loads libcrypto (OpenSSL). Resolution order: (1) openssl.library.path system property, (2) java.home/bin on Windows, java.home/lib elsewhere. Platform filenames: libcrypto-3-x64.dll (Windows/amd64), libcrypto64.so.3 (AIX), libcrypto-semeru.so (fallback). Must be loaded first so the JNI DLL can resolve its OpenSSL symbols.
  • preloadOpenJCEPlusNative() — loads libjgskit_openssl_64.dll/.dylib/.so from jgskit.library.path system property or java.home. This is the DLL that contains all the native methods declared in NativeOpenSSLImplementation.

Context creation — initializeContext()

Called from the constructor. synchronized with a double-checked guard so concurrent provider instantiations only initialize once:

private synchronized void initializeContext() {
    if (osslInitialized) return;                           // guard: already done
    long osslContextId = NativeOpenSSLImplementation.initializeOSSL(useFIPSMode);
    this.osslContext = OpenSSLContext.createContext(osslContextId, useFIPSMode);
    getLibraryBuildDate();                                 // cache build-date immediately
    this.osslInitialized = true;
}

initializeOSSL calls OSSL_provider_load (FIPS) or sets up the default provider, then returns a pointer to a native context struct cast to jlong. OpenSSLContext is a plain value-object wrapper; it has no lifecycle of its own — the native context lives for the JVM lifetime.

getOpenSSLContext() re-triggers initialization if the adapter was deserialized into a JVM that never instantiated the provider (e.g. a serialized HASHDRBG SecureRandom).

Version and path lazy-fetch

getLibraryVersion() / getLibraryInstallPath() call obtainOpenSSLVersion() / obtainOpenSSLInstallPath() if the value is still the sentinel. Each obtainer is synchronized with an inner double-check — the outer check avoids contention in the common (already-fetched) path; the inner synchronized check prevents a duplicate native call when two threads race on first access.

Validation methods

validateLibraryLocation() checks that the canonical path of the loaded libcrypto file starts with the canonical path reported by the native context. validateLibraryVersion() parses the major.minor.patch version string and requires ≥ 3.0.0. Neither method is called during normal initialization; both exist to satisfy the NativeInterface contract (OCK calls them during provider setup).

initialize(boolean isFIPS)

No-op returning 0. OCK uses this to hand back a context ID; for OpenSSL the context is created in the constructor, so there is nothing to do here.

3 · Symmetric Cipher (AES-CBC, AES-CTR, …)

No-op / pass-through for most; Changed for decrypt padding errors and hardware support.

Context lifecycle

The CIPHER_* family maps one-for-one onto NativeOpenSSLImplementation statics, injecting osslContext.getId() as the first argument. Context creation uses EVP_CIPHER_fetch (OpenSSL 3 provider API); the algorithm name string (e.g. "AES-256-CBC") is passed in by the Java caller from LegacyCipher. The C side holds an EVP_CIPHER* + EVP_CIPHER_CTX* pair in a heap-allocated CipherContext struct whose pointer is returned as a jlong (the cipherId).

CIPHER_init(cipherId, isEncrypt, paddingId, key, iv)Direct pass-through; calls EVP_CipherInit_ex with key and IV
CIPHER_clean(cipherId)Pass-through; resets the EVP_CIPHER_CTX without freeing it
CIPHER_setPadding(cipherId, paddingId)Pass-through; calls EVP_CIPHER_CTX_set_padding
CIPHER_getBlockSize / getKeyLength / getIVLength / getOIDPass-through; query methods on the EVP_CIPHER bound to this context

CIPHER_decryptUpdatePass-through; same needsReinit forwarding

CIPHER_decryptFinal — padding exception translation

Changed

OCK's native decrypt throws a Java BadPaddingException directly when PKCS padding is wrong. OpenSSL's EVP layer reports the same condition as a native error string containing "bad padding", which surfaces as an OpenSSLException. The adapter catches it and translates:

try {
    return NativeOpenSSLImplementation.CIPHER_decryptFinal(...);
} catch (OpenSSLException e) {
    String msg = e.getMessage();
    if (msg != null && msg.toLowerCase().contains("bad padding")) {
        BadPaddingException bpe = new BadPaddingException(msg);
        bpe.initCause(e);
        throw bpe;
    }
    throw e; // any other native error propagates as-is
}

The original OpenSSLException is chained as the cause so stack traces are not lost. All other OpenSSLExceptions from CIPHER_decryptFinal propagate unchanged.

4 · AES-GCM

This is the most complex section. The OCK GCM path uses a single ICC_AES_GCM_CTX opaque context and large legacy JNI functions that combine init, AAD, data, and finalize into one call. The OpenSSL path uses thin JNI primitives (GCM_init, GCM_update, GCM_encryptFinal, GCM_decryptFinal) and composes them in Java inside the adapter.

4a · Context creation

Changed

OCK's create_GCM_context() calls ICC_AES_GCM_CTX_new — a key-agnostic allocation. OpenSSL must know the algorithm at context-creation time because EVP_CIPHER_fetch("AES-128-GCM") (or 192/256) is called immediately. Two overloads are provided:

// No-arg overload — satisfies NativeInterface contract; defaults to AES-128-GCM.
// GCMCipher never calls this directly; it always uses the keySize overload.
create_GCM_context():
    → CIPHER_create(osslContextId, "AES-128-GCM")

// keySize overload — called by GCMCipher with the actual key size in bytes.
create_GCM_context(int keySize):
    16 → CIPHER_create(osslContextId, "AES-128-GCM")
    24 → CIPHER_create(osslContextId, "AES-192-GCM")
    32 → CIPHER_create(osslContextId, "AES-256-GCM")
    other → defaults to "AES-128-GCM"

The returned cipherId is a CipherContext* cast to jlong. It is stored in GCMCipher.GCMContextPointer as a ThreadLocal and re-used across multiple operations on the same thread — the context is reset by GCM_init at the start of each operation, not recreated.

4b · Thin JNI primitives

New

Four new native methods in NativeOpenSSLImplementation, implemented in OpenSSLGCM.c. Each receives the osslContextId and cipherId (the CipherContext*) as the first two arguments:

MethodC-side actions
GCM_init(ctxId, cipherId, encrypt, key, iv, tagLen)EVP_CIPHER_CTX_reset → EVP_CipherInit_ex(cipher, NULL, NULL, NULL) (binds algorithm) → if ivLen ≠ 12: EVP_CIPHER_CTX_ctrl(SET_IVLEN) → EVP_CipherInit_ex(NULL, key, iv) (sets key+IV) → stores tagLen in context struct
GCM_update(ctxId, cipherId, encrypt, in, inOff, inLen, out, outOff, aad, aadLen)If aadLen > 0: EVP_CipherUpdate(ctx, NULL, &outl, aad, aadLen) (AAD path — NULL output signals AAD); then if inLen > 0: EVP_CipherUpdate(ctx, out+outOff, &outl, in+inOff, inLen) (data path). Returns bytes written.
GCM_encryptFinal(ctxId, cipherId, in, inOff, inLen, out, outOff, aad, aadLen, tagLen)Optional AAD update → EVP_CipherUpdate for final plaintext block → EVP_CipherFinal_ex → EVP_CIPHER_CTX_ctrl(GET_TAG); writes ciphertext immediately followed by tag into out; returns total bytes written.
GCM_decryptFinal(ctxId, cipherId, in, inOff, inLen, out, outOff, aad, aadLen, tagLen)Optional AAD update → EVP_CipherUpdate for all ciphertext (tag is at the end of in) → EVP_CIPHER_CTX_ctrl(SET_TAG) → EVP_CipherFinal_ex; throws OpenSSLException("GCM tag mismatch") if verification fails.

4c · One-shot encrypt (do_GCM_encrypt)

Changed

OCK's one-shot encrypt is a single native call. OpenSSL composes GCM_init + GCM_encryptFinal in Java:

// 1. Pre-flight checks
if (ciphertextOffset < 0 || inLen < 0 || ciphertextOffset + inLen > ciphertext.length)
    throw OpenSSLException("buffer too small or invalid offset");
if (tagLen < 0 || tagLen > tag.length)
    throw OpenSSLException("tag buffer too small");
int ctxKeyLen = CIPHER_getKeyLength(gcmCtx);
if (ctxKeyLen > 0 && keyLen != ctxKeyLen)
    throw OpenSSLException("key length mismatch");

// 2. Tag-length clamping: OpenSSL GCM_init requires tagLen >= 4.
int nativeTagLen = Math.max(tagLen, 4);

// 3. Init + encrypt
GCM_init(osslContextId, gcmCtx, 1 /*encrypt*/, key, iv, nativeTagLen);
byte[] combinedOutput = new byte[inLen + nativeTagLen];
int totalLen = GCM_encryptFinal(osslContextId, gcmCtx,
                  input, inOffset, inLen, combinedOutput, 0,
                  aad, aadLen, nativeTagLen);

// 4. Split combinedOutput: [ciphertext | tag]
int cipherLen = Math.max(0, totalLen - nativeTagLen);
System.arraycopy(combinedOutput, 0,         ciphertext, ciphertextOffset, cipherLen);
System.arraycopy(combinedOutput, cipherLen, tag,        0,                tagLen);
// Only tagLen bytes are returned to caller — trailing bytes (if nativeTagLen > tagLen) are discarded.

Why combinedOutput? GCM_encryptFinal writes ciphertext and tag contiguously. Splitting them after the fact avoids requiring the caller to pre-arrange their buffers for the native call.

Why tag clamping? OpenSSL's EVP_CIPHER_CTX_ctrl(EVP_CTRL_GCM_SET_TAG) enforces a minimum tag size of 4 bytes. A caller requesting e.g. tagLen=0 (authentication-only mode) must be handled by internally using 4 bytes and then discarding the tag before returning it to the caller.

4d · One-shot decrypt (do_GCM_decrypt)

Changed

The ciphertext and tag arrive as separate regions inside the caller's buffer. OpenSSL's GCM_decryptFinal expects them concatenated. The adapter builds a combinedInput array:

// Pre-flight checks (offset/length bounds + key-length mismatch)
int nativeTagLen = Math.max(tagLen, 4);

// Build combinedInput = ciphertext_bytes ++ tag_bytes ++ zero_padding_if_needed
byte[] combinedInput = new byte[cipherLen + nativeTagLen];
System.arraycopy(ciphertext, cipherOffset,          combinedInput, 0,       cipherLen);
System.arraycopy(ciphertext, cipherOffset + cipherLen, combinedInput, cipherLen, tagLen);
// bytes [cipherLen+tagLen .. cipherLen+nativeTagLen-1] remain zero — acceptable because
// OpenSSL truncates tag verification to the originally-requested tagLen.

GCM_init(osslContextId, gcmCtx, 0 /*decrypt*/, key, iv, nativeTagLen);
GCM_decryptFinal(osslContextId, gcmCtx,
    combinedInput, 0, combinedInput.length,
    plaintext, plaintextOffset,
    aad, aadLen, nativeTagLen);
// GCM_decryptFinal throws OpenSSLException on tag mismatch — no rc check needed.

4e · Multi-part init (do_GCM_InitForUpdateEncrypt/Decrypt)

Changed

Both methods follow the same pattern. For encrypt:

// Key-length validation against the context's baked-in cipher
int ctxKeyLen = CIPHER_getKeyLength(gcmCtx);
if (ctxKeyLen > 0 && keyLen != ctxKeyLen)
    throw OpenSSLException("key length mismatch");

// Initialize the EVP context for this operation
GCM_init(osslContextId, gcmCtx, 1 /*encrypt*/, key, iv, DEFAULT_GCM_TAG_LEN /*=16*/);

// Feed AAD now, into the active context
if (aad != null && aadLen > 0) {
    GCM_update(osslContextId, gcmCtx, 1,
        EMPTY_BYTE_ARRAY, 0, 0,    // zero-length data — GCM_update feeds AAD first
        EMPTY_BYTE_ARRAY, 0,
        aad, aadLen);
}

Why AAD is fed at Init, not Final: OpenSSL requires AAD to be submitted to the context before any data bytes. On the OCK path, AAD was passed into the Final call and re-submitted each time. On the OpenSSL path it is consumed here, during Init, before any GCM_update data calls. This means the Final method must not re-pass AAD (see §4f below).

Why DEFAULT_GCM_TAG_LEN (16)? The multi-part Init does not yet know the final tag length the caller will request at Final time. 16 bytes is the maximum GCM tag length and is always safe — the Final call will use the actual requested tag length when calling GCM_encryptFinal.

4f · Multi-part update (do_GCM_UpdForUpdateEncrypt/Decrypt)

Changed

Each call streams data bytes through the active context using GCM_update. AAD is not re-passed (it was consumed in Init). A negative return value from GCM_update is treated as a hard failure:

int outLen = GCM_update(osslContextId, gcmCtx, 1 /*encrypt*/,
    input, inOffset, inLen, ciphertext, ciphertextOffset, null, 0);
if (outLen < 0)
    throw new OpenSSLException("GCM update (encrypt) failed: " + outLen);
return 0;

OCK's do_GCM_UpdForUpdate* never returns negative values — errors surface as non-zero integer return codes that GCMCipher tests with if (rc != 0). OpenSSL uses the same non-zero-rc convention for the return value, but negative values from EVP_CipherUpdate indicate a hard EVP-level error. The adapter throws immediately rather than returning the negative value to GCMCipher, which would misinterpret it.

4g · Multi-part final (do_GCM_FinalForUpdateEncrypt/Decrypt)

Changed

Encrypt final:

// AAD parameter is intentionally ignored — it was already consumed in InitForUpdate.
// Re-passing it here would double-apply the AAD and produce a wrong authentication tag.
int totalLen = GCM_encryptFinal(osslContextId, gcmCtx,
    input, inOffset, inLen, ciphertext, ciphertextOffset,
    null, 0,   // ← aad suppressed
    tagLen);
if (totalLen != inLen + tagLen)
    throw OpenSSLException("unexpected output length");
// Tag sits at ciphertext[ciphertextOffset + inLen .. +tagLen]; extract it into tag[].
System.arraycopy(ciphertext, ciphertextOffset + inLen, tag, 0, tagLen);

Decrypt final:

// Same AAD suppression.
// Tag-mismatch surfaces as OpenSSLException thrown by GCM_decryptFinal,
// not as a negative rc integer — GCMCipher's rc check is bypassed.
GCM_decryptFinal(osslContextId, gcmCtx,
    ciphertext, cipherOffset, cipherLen,
    plaintext, plaintextOffset,
    null, 0,   // ← aad suppressed
    tagLen);
return 0;
AAD suppression detail: GCMCipher used to track an initCalled flag and null the aad field before calling FinalForUpdate*. That flag has been removed; the suppression is now unconditional inside these adapter methods — the aad parameter is simply ignored regardless of what the caller passes.

4i · FastJNI / hardware stubs

Stub

do_GCM_checkHardwareGCMSupport() returns -1 unconditionally, signalling to GCMCipher that no hardware acceleration pointer is available. All four FastJNI methods throw UnsupportedOperationException:

  • do_GCM_encryptFastJNI_WithHardwareSupport
  • do_GCM_encryptFastJNI
  • do_GCM_decryptFastJNI_WithHardwareSupport
  • do_GCM_decryptFastJNI

GCMCipher guards the FastJNI branch with GCMHardwareFunctionPtr != -1, so these methods are never reached at runtime on the OpenSSL backend.

5 · AES-CCM

Changed

CCM uses a per-call context pattern instead of the OCK cached-context approach. Each do_CCM_encrypt / do_CCM_decrypt call creates a fresh CipherContext, runs CCM_init + CCM_encryptFinal or CCM_decryptFinal, then frees the context in a finally block — regardless of whether the operation succeeded or threw.

5a · Thin JNI primitives

New

Four analogous primitives in NativeOpenSSLImplementation implemented in OpenSSLCCM.c:

MethodC-side actions
CCM_init(ctxId, cipherId, encrypt, key, iv, tagLen)EVP_CIPHER_CTX_reset → set tag length via EVP_CIPHER_CTX_ctrl(SET_TAG) (CCM requires tag length before key/IV) → set IV length if non-standard → EVP_CipherInit_ex(key, iv)
CCM_updateReserved for future streaming CCM use; not called by current adapter code (CCM is always one-shot)
CCM_encryptFinal(ctxId, cipherId, in, inOff, inLen, out, outOff, aad, aadLen, tagLen)If aadLen > 0: set total plaintext length via EVP_CipherUpdate(NULL) (CCM requirement) → feed AAD → EVP_CipherUpdate for plaintext → appends tag to output; returns total bytes written
CCM_decryptFinal(ctxId, cipherId, in, inOff, inLen, out, outOff, aad, aadLen, tagLen)Same pattern; passes expected tag (trailing bytes of in) to EVP_CIPHER_CTX_ctrl(SET_TAG) before decryption; throws on tag mismatch

5b · Key-size selection helper

Because CCM contexts are not cached (a new context is created per call), the algorithm name must be selected at call time. The private helper getAESCipherAlgorithm(int keyLen, String mode) maps:

getAESCipherAlgorithm(keyLen, "CCM"):
    16 → "AES-128-CCM"
    24 → "AES-192-CCM"
    32 → "AES-256-CCM"

5c · Encrypt (do_CCM_encrypt)

long cipherId = CIPHER_create(osslContextId, getAESCipherAlgorithm(keyLen, "CCM"));
try {
    // Pre-flight: ciphertext buffer must be large enough for inLen + tagLen bytes.
    if (ciphertext.length < inLen + tagLen)
        throw OpenSSLException("CCM encrypt: ciphertext buffer too small");
    CCM_init(osslContextId, cipherId, 1 /*encrypt*/, key, iv, tagLen);
    CCM_encryptFinal(osslContextId, cipherId,
        input, 0, inLen, ciphertext, 0,
        aad, aadLen, tagLen);
    return 0;
} finally {
    CIPHER_delete(osslContextId, cipherId); // always free, even on exception
}

5d · Decrypt (do_CCM_decrypt)

Same structure as encrypt. The combined ciphertext+tag buffer is passed directly; CCM_decryptFinal extracts the tag from the end of the input.

5e · Hardware / FastJNI stubs

Stub

do_CCM_checkHardwareCCMSupport() returns -1. All four FastJNI CCM methods throw UnsupportedOperationException. CCMCipher guards these with CCMHardwareFunctionPtr != -1 — since the adapter returns -1, the FastJNI branch is never entered. The non-FastJNI else branch in CCMCipher is the only path taken for the OpenSSL backend, and it calls do_CCM_encrypt / do_CCM_decrypt above.

5f · Cleanup

do_CCM_delete() is a no-op — CCM contexts are freed inline after each encrypt/decrypt call inside the finally block. There is no persistent per-thread CCM context to tear down.

6 · Poly1305 Cipher

Stub

All nine POLY1305CIPHER_* methods throw UnsupportedOperationException("... not yet implemented in OpenSSL backend"). The corresponding native declarations exist in NativeOpenSSLImplementation but their C implementations are not yet present in OpenSSLSymmetricCipher.c.

8 · Exception Translation

OCK uses OCKException extends NativeException. The OpenSSL backend uses OpenSSLException extends NativeException. Both satisfy the NativeInterface contract which declares throws NativeException. Translation is needed only where JCE callers catch a specific checked exception type:

SiteTranslationReason
CIPHER_decryptFinalOpenSSLException("bad padding") → BadPaddingExceptionOCK throws BadPaddingException directly from native; callers catch it by type
do_GCM_FinalForUpdateDecryptNo translation — OpenSSLException from tag mismatch propagates as-isOCK returned negative rc; GCMCipher has been updated to catch NativeException for this path
do_GCM_UpdForUpdateEncrypt/DecryptNegative int from GCM_update → OpenSSLException thrown immediatelyOCK never returns negative from update; the adapter normalises the contract so GCMCipher never sees a negative rc
